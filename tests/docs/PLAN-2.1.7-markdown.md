2026-10-12 已复现：14pt sans 默认字体产生多个同名 PingFang Type3 字体。Type3 字体通过不同字符表及 CharProcs 描述字形，字体名称不能唯一标识资源。原定位器仅凭名称匹配，原指令路径拒绝歧义，替换路径又取第一个字体，导致正常文字被误判为 ui.nativeTextStale。编辑区域按 loadedName 分割，进一步把同一字体的字符子集拆成单字。serif 同样操作成功，sans 失败，解释了此前测试为什么漏掉。

1. 共享定位器按资源的 ToUnicode 字符表绑定同名字体，正确记录字形位置和指令；预览与应用共用。为 Type3 保留类型信息，按真实字体合并其子集，仍保存每片文字的源字体定位。
2. 原字形不能直接复用时自动使用既有矢量排版路径；补齐 PingFang 字体族名称，并复用现有字体类别映射，避免无衬线文字被换成宋体。保留精确字号、原基线、未编辑文本和历史。
3. 进入编辑前先加载完整绘制指令的字体信息，字体/定位差异自动处理，不使用通用失败弹窗。实际保存或系统操作失败在编辑器内反馈并保留草稿。
4. 新增用户实际 Markdown、sans/serif、重复编辑、字号/颜色、保存 PDF 后继续编辑、撤销重做、链接和邻文像素隔离的关键验收；同时覆盖同名字体的字符表、Type3 子集与多语言文本。
5. 仅执行本次关键测试和受影响的已有关键信息，不跑旧测试全集；重新构建 macOS arm64 APP/DMG/ZIP，实际运行新成品验收，更新报告与校验值。

进一步确认：PDF.js 将多个 Type3 子集聚合为一个 TextItem，仅报告第一个 fontName；必须从完整 OperatorList 收集字体，并按实际同字体的字形序列匹配。收集依赖与 ExtGState 字体，合并 Type3 字体宽度表，覆盖连续编辑及部分字符未单独产生 TextItem 的情况。

衬线连续编辑补充：同一可见字体的原程序与补字是不同 PDF 字体资源，不能以 loadedName 不同拆成两套重叠编辑框。按字体族、字重、字形和字号分组，保留各片源绑定。Chromium 的 Type3 输出没有 BaseFont 时，打印输出的 Unicode 还原也必须读取 FontDescriptor.FontName，避免原标点仍复制为私有区字形。

连续编辑时，同名的新补字子集可能是原大子集的一部分；仅要求候选含有该子集的字符仍有歧义，必须优先完整字符表相等。打印窗口把程序 PostScript 名中的加号改为下划线，并新增子集前缀；还原 Unicode 时对该改写做精确匹配。补字合行只允许相同物理字体名称（忽略子集前缀和本应用输出标识），不混合仅归一到同一字体族的不同实际字体。
